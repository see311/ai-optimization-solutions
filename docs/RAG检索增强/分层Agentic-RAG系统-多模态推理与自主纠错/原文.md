# Building Hierarchical Agentic RAG Systems: Multi-Modal Reasoning with Autonomous Error Recovery

> 作者：Abhijit Ubale | 发布日期：2026-04-09

## 核心要点

### 模态鸿沟问题
传统 RAG 系统在处理结构化数据（SQL）和非结构化数据（文档）时存在"模态鸿沟"：
- **结构化推理**：需要 SQL 数据库查询（收入、利润率、客户数量等）
- **语义检索**：需要向量搜索（市场报告、竞品分析、法规文档等）
- **跨模态综合**：将 SQL 结果与文档洞察关联

传统 RAG 只能"一次完成"，导致答案不完整或产生幻觉。

### 分层 Agentic 解决方案

**Protocol-H** 引入 Supervisor-Worker 拓扑结构：

```
┌─────────────────────────────────────────────────────┐
│                    Supervisor                        │
│              (元认知编排器)                           │
│  • 查询分析  • 任务分解  • Worker路由  • 结果综合    │
└─────────────────────────────────────────────────────┘
          │                        │
          ▼                        ▼
┌──────────────────┐    ┌──────────────────┐
│    SQL Worker    │    │   Vector Worker   │
│  (Schema感知查询) │    │   (语义检索智能体) │
│  • Schema自省    │    │  • 混合检索(BM25+ │
│  • 查询校验      │    │    向量+RRF融合)  │
│  • 方言优化      │    │  • 相关性过滤     │
│  • 安全机制      │    │  • 摘要提取       │
└──────────────────┘    └──────────────────┘
```

### Supervisor 核心职责

1. **查询分析**：判断问题需要 SQL、语义检索还是两者
2. **任务分解**：拆解复杂查询为原子步骤
3. **Worker路由**：基于任务和当前状态决定下一步
4. **结果综合**：整合各 Worker 输出为连贯答案
5. **错误管理**：检测失败并触发 Reflective Retry

### SQL Worker 特性

**Schema 自省**
- 通过 `INFORMATION_SCHEMA` 自动发现表和列
- 两种关系识别机制：
  - 显式外键约束（权威来源）
  - LLM 启发式推断（基于列命名规范）

**多层防护降低推断风险**
1. 置信度评分：低置信度推断（相似度 < 0.8）要求显式确认
2. Supervisor 仲裁：推断关系作为候选建议提交
3. 运行时验证：先以行数受限形式执行，异常则触发重试
4. 显式外键优先：存在显式外键时跳过启发式推断

**安全机制**
- SQL 注入防护：参数化查询 API
- 行级访问控制：使用数据库原生 RBAC
- 查询超时保护：默认 30 秒超时
- 结果大小限制：防止上下文溢出

### Vector Worker 特性

**混合检索**
- BM25 关键词匹配 + 稠密向量余弦相似度
- RRF（Reciprocal Rank Fusion）融合排序
- 平衡精确性（精确词命中）与召回（概念相关内容）

**关键挑战处理**
- **冷启动问题**：无相关文档时返回 null 信号，触发回退
- **歧义处理**：将 Top-N 结果及相关性分数提交 Supervisor 仲裁
- **时间感知**（可选）：时间衰减因子使近期文档优先

### Reflective Retry 机制

**核心差异**：当 Worker 遇到错误时，系统进入 Reflective Retry 模式，而非将错误传播为幻觉。

```python
class RetryCorrection(BaseModel):
    corrected_query: Optional[str] = None
    alternative_strategy: Optional[str] = None

def reflective_retry_node(state: AgentState) -> Dict[str, Any]:
    error_msg = state.error_message
    # LLM 分析错误并建议修正方案
    correction = llm.with_structured_output(RetryCorrection).invoke(retry_prompt)
    return attempt_alternative_approach(correction)
```

**效果**：幻觉率从 28.5% 降至 7.1%（降低约 60%）

### 生产部署要点

**StateGraph 状态管理**
- 确定性的工作流编排
- 全链路可审计追溯
- 带重试计数器和超时的安全保护

**云无关数据库适配器**
- Adapter 模式抽象数据库特性
- 支持 Snowflake、Redshift、BigQuery 等
- 统一 QueryResult 接口

**合规与安全**
- 确定性的控制流满足审计要求
- Schema 感知防止越权查询
- 策略控制（如 schema_policy.yaml）
- 完整错误诊断

### 经验总结

1. **专业化优于通用化**：专用 SQL/Vector Worker 优于单一通用 Agent
2. **错误恢复至关重要**：60% 幻觉源于未处理的执行错误，而非 LLM 推理缺陷
3. **Schema 感知是关键**：了解可用数据的 Worker 决策更优
4. **确定性启用信任**：企业更看重可重现执行，而非最高准确率
5. **多模态推理需要编排**：分层委托机制必不可少

### 未来方向

- **自适应路由**：基于历史日志学习最优 Worker 组合
- **语义缓存**：缓存向量搜索结果减少冗余嵌入
- **跨模态融合**：更复杂的方法结合 SQL 和语义证据
- **可解释性**：生成人类可读的多跳推理路径解释
