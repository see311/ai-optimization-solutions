# RAG 优化实战 - query 改写与 prompt 构建

> 总结使用: MiniMax M2.5

## 一、为什么原始 query 不能直接检索？

用户的口语化提问与知识库的专业文档存在**语义鸿沟**，导致检索失败。

**5种难检索场景：**

| 场景 | 示例 | 问题 |
|------|------|------|
| 口语化表达 | "上次那个报错怎么解决的" | 模糊指代，无关键词 |
| query过于笼统 | "介绍一下你们的产品" | 向量指向模糊区域 |
| 多子问题 | "对比MySQL和PG的差异及锁机制" | embedding被"平均化" |
| 多轮指代 | "它的优化方法有哪些？" | 无法识别指代对象 |
| 拼写/缩写错误 | "LangChian"、"RAGg" | 无法识别核心语义 |

## 二、5种 Query 改写策略

### 1. 指代消解与上下文补全
- **场景**：多轮对话
- **方法**：将当前query与对话历史结合，生成完整独立的query
- **优化**：先用规则判断是否包含指代，再决定是否调用大模型

### 2. 查询分解 (Query Decomposition)
- **场景**：复合query包含多个子问题
- **方法**：拆分成多个独立的子query分别检索
- **实现**：基于规则（快但死板）或基于大模型（灵活）

### 3. 多角度改写 (Multi-Query)
- **场景**：提升召回率
- **方法**：生成3-5个语义相同但措辞不同的query变体
- **注意**：成本高，仅在检索结果不达标时触发

### 4. HyDE (Hypothetical Document Embeddings)
- **场景**：表述风格差异大
- **方法**：先生成假想答案文档，用其embedding检索
- **原理**：假想文档与真实文档风格一致，匹配度更高

### 5. Step-back Prompting
- **场景**：需要背景知识才能回答
- **方法**：将具体query抽象化，检索更全面的背景知识

## 三、工程选型：按需改写

### 四级处理策略

| 级别 | query类型 | 处理方式 |
|------|-----------|----------|
| 第一级 | 简单query | 直接检索 |
| 第二级 | 有指代/省略 | 仅指代消解 |
| 第三级 | 复合query | 指代消解 + 查询分解 |
| 第四级 | 检索结果差 | 多角度改写/HyDE |

### 优化技巧
- 缓存复用高频query
- 控制query变体数量（3-5个）
- 选择轻量级大模型（如GPT-3.5、通义千问）

## 四、Prompt 构建：4个核心环节

### 1. 重排序 (Reranking)
- 用Reranker模型精细打分
- 常用模型：Cohere Rerank、bge-reranker
- **关键**：最相关文档放开头和结尾（应对"Lost in the Middle"）

### 2. 上下文压缩
- 提取核心信息，去除冗余
- LangChain提供 ContextualCompressionRetriever 组件

### 3. Prompt 模板三要素

```
1. 角色指令：只能使用检索文档中的信息
2. 引用规范：用[1][2]标注信息来源
3. 幻觉约束：不知道就说不知道
```

### 4. 冲突处理
- 优先级排序：最新文档 > 官方文档
- 逻辑排序：按信息逻辑顺序排列

## 五、兜底方案

### 1. 相关性判断与降级
- 阈值判断（如0.6），低于阈值触发降级
- 降级策略：坦诚告知无法回答，或标注"仅供参考"

### 2. 混合检索
- 向量检索 + 关键词检索(BM25)
- 用 RRF (Reciprocal Rank Fusion) 算法融合
