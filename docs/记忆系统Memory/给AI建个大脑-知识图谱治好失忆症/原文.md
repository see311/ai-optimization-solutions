# 什么是 Ontology？

**Ontology** （本体论），听起来玄乎，实际上就是——**给AI建一套结构化的知识图谱** 。

不是简单地把信息存成文本，而是用"实体+类型+关系"的模式，把知识像蜘蛛网一样编织起来：

```
张伟 (Person) 

 └── 负责 → 河狸工坊 (Project) 

 └── 包含 → 产品设计 (Task) 

 └── 被阻塞 → Logo定稿 (Task)
```

这就是一个**图结构** ，而不是一堆散乱的文字。

# ⚙️ 它是怎么工作的？

# 一切皆"实体"（Entity）

每个东西都是实体，有类型、属性和关系：

```
# 创建一个人

Person {

 id: "p_001",

 name: "张伟",

 email: "zhangwei@example.com",

 role: "产品负责人"

}

# 创建一个项目

Project {

 id: "proj_001", 

 name: "河狸工坊",

 status: "active",

 goals: ["MVP上线", "获取100个用户"]

}
```

支持的类型相当丰富：

| 类型 | 用途 |

|------|------|

| `Person` | 联系人、团队成员 |

| `Project` | 项目 |

| `Task` | 任务（含状态、优先级、阻塞关系）|

| `Event` | 日程事件 |

| `Document` | 文档 |

| `Credential` | 凭证（密码永远不明文存储）|

# 关系才是精髓

光有实体不够，**关系才是知识** ：

```
# 把人关联到项目（这个人是项目Owner）

ontology relate --from proj_001 --rel has_owner --to p_001

# 给项目添加任务

ontology relate --from proj_001 --rel has_task --to task_001

# 标记阻塞关系（这个任务被另一个阻塞）

ontology relate --from task_blocker --rel blocks --to task_001
```

**关系类型** 有约束：

- `has_owner`：从 Project/Task 指向 Person，**多对一** （一个项目只能有一个负责人）

- `blocks`：Task → Task，**不能有环** （你不能让A阻塞B、B阻塞C、C又阻塞A）

类型系统会自动校验这些约束——就像TypeScript的类型检查，但检查的是你的业务逻辑。

# 最惊艳的功能：把规划变成图变换

这是我觉得最有意思的部分。

当你跟AI说"帮我规划一下河狸工坊的启动流程"，它可以把规划建模成**一系列图操作** ：

```
张伟 (Person) 

 └── 负责 → 河狸工坊 (Project) 

 └── 包含 → 产品设计 (Task) 

 └── 被阻塞 → Logo定稿 (Task)
```

**每一步都经过验证** 。如果违反了约束（比如给一个已关闭的任务添加新依赖），系统会回滚——而不是静默生成一个矛盾的规划。

这才是AI规划应有的样子：**可验证、可追溯、不自相矛盾** 。

# 安全设计很到位

`Credential` 类型的实体有一条黄金法则：

> **禁止存储明文密码/密钥，永远用间接引用。**

```
# schema.yaml 中 Credential:

  forbidden_properties: [password, secret, token] 
```

这意味着如果你不小心让AI输出一个凭证对象，它会直接报错——而不是把密钥泄露到对话里。

对于需要调用外部API的场景，这个安全设计是刚需。

# 对AI开发者的意义

如果你在开发AI应用，`ontology` 提供了一个**跨Skill共享状态** 的协议：

```
# 创建一个人

Person {

 id: "p_001",

 name: "张伟",

 email: "zhangwei@example.com",

 role: "产品负责人"

}

# 创建一个项目

Project {

 id: "proj_001", 

 name: "河狸工坊",

 status: "active",

 goals: ["MVP上线", "获取100个用户"]

}
```

邮件Skill和任务Skill不需要互相知道对方的存在，只需要遵守同一个"本体协议"——这就是**Skill可组合性** 的基础设施。

# 快速上手

```
# 初始化

mkdir -p memory/ontology

touch memory/ontology/graph.jsonl

# 创建一个人

ontology create --type Person --props '{"name":"张伟"}'

# 查询所有任务

ontology query --type Task --where '{"status":"open"}'

# 查看某个项目的所有依赖

ontology related --id proj_001 --rel has_task

# 验证完整性（检查循环依赖等）

ontology validate
```

# 总结

`ontology` 解决的不是"AI记忆差"这个表面问题，而是**AI知识表示的根本问题** 。

它让AI的"记忆"变成了一张**可查询、可验证、可组合** 的结构化网络，而不是一串随时会蒸发的上下文Token。

对于那些需要AI处理复杂项目、多角色协作、长期跟踪任务的场景——这才是真正的游戏改变者。
