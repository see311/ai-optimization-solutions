# 封神级 RAG 优化实战，query 改写 + prompt 构建，吃透面试核心考点

> 来源：今日头条 - AI码韵匠道
> 发布时间：2026年5月5日
> 京东科技软件工程师

在大模型面试中，RAG（检索增强生成）系统是高频考点，尤其是涉及实际落地效果优化的问题，更是面试官判断候选人工程能力和技术深度的关键。有这样一个极具针对性的问题：RAG系统中如何进行query改写，以及如何基于检索结果构建有效prompt？

很多开发者在搭建RAG系统时，很容易陷入一个误区，把大量精力都投入到embedding模型选型、向量库调参上，却忽略了两个看似基础却能直接决定系统效果的环节：query改写和检索结果的prompt组织。最终往往出现这样的困境，知识库里明明有对应的答案，检索时却死活找不到；或者检索到了相关文档，大模型输出的回答依然偏离预期、漏洞百出。

其实这两个环节，分别对应着RAG管线中的检索前优化和生成前优化，是提升RAG端到端效果最直接、成本最低的手段。今天我们就结合面试考点和实战经验，详细拆解这两个核心环节，帮大家理清思路，不仅能从容应对面试提问，更能在实际项目中落地应用，打造出高性能的RAG系统。

## 一、先搞懂：为什么原始query不能直接用于检索？

要做好query改写，首先得明白一个核心问题，为什么我们不能把用户输入的原始query直接丢给检索引擎？答案很简单，用户的提问方式和知识库中文档的表述方式，往往存在巨大的语义鸿沟，这种鸿沟会直接导致检索召回率偏低，甚至检索失败。

我们可以从日常使用场景出发，举几个最常见的例子。比如用户在工作中遇到报错，可能会输入"上次那个报错怎么解决的"，这句话是典型的口语化表达，里面包含了"上次""那个"这样的模糊指代，没有任何明确的技术关键词；而知识库中对应的文档，大概率会用规范的专业表述，比如"ConnectionTimeoutException 异常的排查步骤与解决方案"。一边是口语化、带省略、带指代的提问，一边是结构化、规范化的专业文档，直接用原始query做embedding检索，两者的向量相似度会非常低，自然无法精准召回相关文档。

除了这种表述差异带来的问题，还有几种常见的"难检索"场景，也是面试中高频提到的考点，大家一定要重点掌握。

**第一种是query过于笼统。** 比如用户提问"介绍一下你们的产品"，这种问题没有任何明确的聚焦点，对应的embedding向量在高维空间中会指向一个非常模糊的区域，检索引擎无法判断用户到底想了解产品的哪个方面，是功能、价格、使用场景还是技术原理，最终只能返回一堆相关性极低的文档，甚至遗漏核心信息。

**第二种是query包含多个子问题。** 比如用户提问"对比MySQL和PostgreSQL在高并发写入下的性能差异，以及各自的锁机制有什么不同"，这个问题看似简单，实则包含两个独立的子话题：高并发写入性能对比、锁机制差异。如果把这个复合query作为一个整体去做embedding，向量会被两个子话题"平均化"，导致两个子话题的检索精度都大打折扣，可能只能检索到其中一个子话题的相关文档，另一个子话题则会被遗漏。

**第三种是多轮对话中的指代问题，** 这也是生产环境中最容易踩坑的场景。比如用户第一轮提问"RAG是什么"，得到回答后，第二轮接着问"它的检索阶段有哪些优化方法"，这里的"它"指代的是上一轮提到的RAG系统。如果不做任何处理，直接把"它的检索阶段有哪些优化方法"作为query去检索，检索系统根本无法识别"它"的具体指代对象，自然无法精准召回相关文档，导致多轮对话无法正常进行。

还有一种容易被忽略的场景，就是用户query存在拼写错误、缩写不规范等问题。比如用户把"LangChain"写成"LangChian"，把"RAG"写成"RAGg"，或者用行业内不通用的缩写，这些都会导致检索引擎无法正确识别query的核心语义，进而影响检索效果。

正是因为这些问题的存在，query改写才成为RAG系统中不可或缺的检索前优化环节。它的核心目标，就是消除用户表达与知识库表述之间的语义鸿沟，让query更贴合知识库的文档风格，更精准地传递用户的真实需求，从而提升检索的召回率和精度。

## 二、实战落地：RAG系统中主流的query改写策略

理解了为什么需要进行query改写后，接下来就是最核心的部分，实战中常用的query改写策略有哪些，以及每种策略适合什么场景、如何落地。面试中，面试官不仅会问你知道哪些策略，还会追问每种策略的原理、适用场景和工程实现细节，所以这部分内容一定要吃透。

需要注意的是，这些策略并不是互斥的，在实际项目中，我们往往需要根据具体场景，将多种策略组合使用，才能达到最佳的改写效果。下面我们就逐一拆解每种主流策略，结合具体案例，让大家既能理解原理，又能快速落地。

### 2.1 指代消解与上下文补全：多轮对话的刚需

指代消解与上下文补全，是多轮对话场景下最基础、最必须做的改写策略，没有之一。它的核心思路是，将当前轮用户的query，与前几轮的对话历史结合起来，通过大模型的处理，生成一个语义完整、不依赖任何上下文的独立query，消除其中的指代、省略等问题。

前面我们提到的例子，用户第一轮问"RAG是什么"，第二轮问"它的检索阶段有哪些优化方法"，通过指代消解与上下文补全，就可以把第二轮的query改写成"RAG系统的检索阶段有哪些优化方法"。看似简单的一步，却能直接解决多轮对话中检索失效的问题，在生产环境中几乎是必做的环节。

那么具体如何实现呢？其实很简单，我们可以借助大模型（比如GPT-3.5、通义千问等），设计一个简单的prompt，将对话历史和当前query一起输入给大模型，让它输出完整的独立query。

Prompt示例：

```
请你作为query改写助手，将当前用户的query与对话历史结合，进行指代消解和上下文补全，生成一个语义完整、不依赖上下文的独立query。要求：
1. 消除所有指代（如它、这、那等），替换为具体的指代对象；
2. 补全省略的信息，确保query语义完整；
3. 不改变用户的原始需求；
4. 语言简洁，符合知识库文档的表述风格。

对话历史：
用户：RAG是什么？
助手：RAG（Retrieval-Augmented Generation）即检索增强生成，是一种结合了检索和生成的大模型应用技术，通过检索外部知识库的相关信息，辅助大模型生成更准确、更具时效性的回答。

用户当前query：它的检索阶段有哪些优化方法？

改写后的独立query：RAG系统的检索阶段有哪些优化方法？
```

通过这个prompt，大模型就能精准地将"它"替换为"RAG系统"，生成完整的query。

在工程实现上，我们需要维护一个对话历史的缓存，每次用户发起新的查询时，先判断是否为多轮对话（即对话历史不为空），如果是，就将对话历史和当前query一起输入给大模型，进行指代消解和上下文补全；如果是单轮对话，且query没有指代和省略，就可以直接跳过这一步，进入后续的检索环节。

这里有一个优化点，为了降低大模型调用的成本，我们可以先通过简单的规则判断当前query是否包含指代（如"它""这""那""该"等关键词），如果不包含，就直接跳过指代消解，只有包含指代时，才调用大模型进行处理。

### 2.2 查询分解（Query Decomposition）：解决复合问题检索难题

查询分解，顾名思义，就是将一个包含多个子问题的复合query，拆分成多个独立的子query，然后对每个子query分别进行检索，最后将所有检索结果汇总，为后续的prompt构建和回答生成提供支撑。

举个例子，用户提问"对比MySQL和PostgreSQL在高并发写入下的性能差异，以及各自的锁机制有什么不同"，通过查询分解，可以将这个复合query拆分成四个独立的子query：

- MySQL在高并发写入场景下的性能表现
- PostgreSQL在高并发写入场景下的性能表现
- MySQL的锁机制详解
- PostgreSQL的锁机制详解

查询分解的实现方式主要有两种：

1. **基于规则的分解**：适合一些结构相对固定的复合query，比如包含"和""与""对比""以及"等关键词的query，通过正则表达式拆分。优点是速度快、成本低，缺点是灵活性差。

2. **基于大模型的分解**：灵活性高，能处理各种复杂的复合query。

Prompt示例：

```
请你作为query分解助手，将用户的复合query拆分成多个独立的子query。要求：
1. 每个子query只能包含一个核心问题，语义完整、聚焦；
2. 所有子query的组合，能完整覆盖用户原始query的需求，不遗漏任何子话题；
3. 子query语言简洁，符合知识库文档的表述风格，避免口语化；
4. 不要添加任何额外的解释，只输出拆分后的子query，每个子query占一行。

用户原始query：对比MySQL和PostgreSQL在高并发写入下的性能差异，以及各自的锁机制有什么不同。

拆分后的子query：
```

### 2.3 多角度改写（Multi-Query）：提升检索召回率的关键

多角度改写，也叫多query生成，它的核心思路是，针对用户的原始query，通过大模型生成3-5个语义相同但措辞不同的query变体，然后用这些query变体分别进行检索，最后将所有检索结果合并、去重，从而提升检索的召回率。

举个例子，用户原始query是"LangChain如何实现RAG功能"，通过多角度改写，可以生成以下几个query变体：

- LangChain框架实现RAG系统的步骤
- 基于LangChain开发RAG功能的方法
- 如何用LangChain搭建RAG应用
- LangChain中RAG功能的实现原理与实践

用这四个query变体分别进行检索，然后将检索结果合并去重，就能比只用原始query检索，召回更多相关的文档片段。

Prompt示例：

```
请你作为query改写助手，针对用户的原始query，生成5个语义相同但措辞不同的query变体。要求：
1. 所有变体的语义必须与原始query一致，不改变用户的原始需求；
2. 措辞多样化，覆盖不同的表述风格（如专业表述、简洁表述等），避免重复；
3. 语言规范，符合知识库文档的表述风格，避免口语化；
4. 不要添加任何额外的解释，只输出5个query变体，每个变体占一行。

用户原始query：LangChain如何实现RAG功能？

生成的query变体：
```

### 2.4 HyDE（Hypothetical Document Embeddings）：巧妙解决表述风格差异问题

HyDE，即假想文档嵌入，是一种非常巧妙的query改写策略。它不直接改写query本身，而是让大模型先根据原始query，"假想"出一篇可能的答案文档，然后用这篇假想文档的embedding去做检索。

这种策略的核心原理是，假想答案文档和知识库中的真实答案文档，在表述风格上是一致的，都是"文档体"的规范表述，而用户的原始query往往是口语化、简洁化的表述。因此，用假想文档的embedding去检索，比用原始query的embedding去检索，能更好地匹配知识库中的真实文档。

Prompt示例：

```
请你作为假想文档生成助手，根据用户的原始query，生成一篇假想的答案文档。要求：
1. 文档内容围绕query的核心需求展开，覆盖可能的答案要点；
2. 表述风格与知识库中的专业文档一致，规范、严谨，避免口语化；
3. 文档长度控制在300-500字，不要过长；
4. 不要添加任何额外的解释，只输出假想文档。

用户原始query：怎么解决RAG检索不到相关文档的问题？

假想文档：
```

### 2.5 Step-back Prompting：抽象query，覆盖更全面的背景知识

Step-back Prompting，即回溯提示，是一种与多角度改写、查询分解相反的策略。它的核心思路是，不把query变得更具体，而是把query变得更抽象，通过抽象后的query，检索到更全面的背景知识。

举个例子，用户提问"Python 3.9中walrus operator有哪些使用限制"，通过Step-back Prompting，可以将这个具体的query抽象成"Python赋值表达式的语法规则和使用限制"。这个抽象后的query，能检索到关于Python赋值表达式的整体背景知识。

## 三、工程选型：query改写策略的组合与落地技巧

### 3.1 策略组合的核心思路

一个典型的query改写组合思路：

1. 先做指代消解与上下文补全，保证query的语义完整
2. 然后判断query是否为复合query，如果是，就进行查询分解
3. 最后，对每个子query判断检索结果的质量，如果质量达标，就直接进入后续环节；如果质量不达标，再触发多角度改写或HyDE

### 3.2 分级处理策略

**第一级：简单query**。单句、无指代、目标明确、表述规范，不需要做任何改写。

**第二级：有指代或省略的query**。只需要做指代消解与上下文补全。

**第三级：复合query**。需要先做指代消解（如果有），再进行查询分解。

**第四级：检索结果质量不达标**。触发多角度改写或HyDE，进行补充检索。

### 3.3 工程落地的优化技巧

1. **缓存复用**：对于高频query，缓存改写结果和检索结果
2. **控制改写复杂度**：根据场景调整query变体数量和假想文档长度
3. **选择合适的大模型**：query改写不需要GPT-4，用轻量级模型即可

## 四、进阶优化：基于检索结果构建有效prompt

这个环节的核心矛盾是，检索回来的文档可能很多、很长，包含大量的冗余信息，而大模型的上下文窗口是有限的，同时还存在"Lost in the Middle"（中间信息丢失）现象。

### 4.1 重排序（Reranking）：筛选最相关的检索结果

重排序的核心思路是，用专门的重排序模型（Reranker），将用户的query和每个检索到的文档片段拼在一起，进行精细的相关性打分，然后根据打分结果，对文档片段进行重新排序。

常用Reranker模型：
- Cohere Rerank（闭源API，精度高）
- bge-reranker（开源模型，成本低）
- Sentence-BERT Cross-Encoder

**重要细节**：不要严格按照相关性分数降序排列文档片段，而是应该把最相关的2-3个文档片段放在prompt的开头和结尾，中间放次相关的文档片段，应对"Lost in the Middle"现象。

### 4.2 上下文压缩（Context Compression）：去除冗余，提升信息密度

上下文压缩的核心思路是，用大模型或专门的压缩模型，从每个检索到的文档片段中，提取与query直接相关的信息，去掉无关的冗余内容。

Prompt示例：

```
请你作为上下文压缩助手，从以下文档片段中，提取与query直接相关的核心信息，去掉无关的冗余内容。要求：
1. 只保留与query相关的信息，不添加任何额外内容；
2. 语言简洁、连贯，保持原有的专业表述风格；
3. 不改变原文的核心意思；
4. 压缩后的内容控制在100-200字，避免过长。

query：如何优化RAG系统的检索召回率？

文档片段：[文档内容]

压缩后的核心信息：
```

### 4.3 Prompt模板设计：引导大模型有效利用检索信息

一个完整的RAG prompt模板，通常包含三个关键要素：

1. **明确的角色指令**：告诉大模型只能使用检索文档中的信息，不能编造
2. **检索文档的引用格式规范**：要求标注信息来源，如[1][2]等
3. **"不知道就说不知道"的显式约束**：如果检索文档中没有相关信息，直接告知用户

完整Prompt模板示例：

```
请你作为RAG回答助手，严格按照以下要求回答用户的问题：
1. 回答必须完全基于以下提供的检索文档片段，只能使用文档中存在的信息，不能使用自身的知识，不编造任何未在文档中出现的内容；
2. 回答时，需要在相关内容后标注信息来源，格式为[数字]，数字对应文档片段的序号；
3. 如果检索文档中没有相关信息，或者信息不足以回答用户的问题，直接回复"未找到相关信息，无法为你提供准确回答"；
4. 回答语言简洁、连贯、通俗易懂，结构清晰，分点说明（如果需要）；
5. 不要添加任何与回答无关的内容。

用户问题：{user_query}

检索文档片段：
文档1：{document_1}
文档2：{document_2}
文档3：{document_3}

你的回答：
```

### 4.4 文档片段冲突处理：避免大模型混淆

针对文档片段的冲突，我们可以采取两种处理方式：

1. **优先级排序**：明确告诉大模型优先参考哪些文档片段（如最新版本的文档、官方文档）
2. **逻辑排序**：当文档片段之间存在逻辑递进关系时，按照逻辑顺序排列

## 五、兜底方案：检索结果不够好时怎么办？

### 5.1 相关性判断与降级策略

在prompt构建前，增加一个相关性判断环节。用Reranker模型或大模型对检索结果进行二次打分，如果最高分都低于预设的阈值，就执行降级策略：

- **策略一**：让大模型基于自身知识回答，但必须明确标注"以下回答未基于知识库验证，仅供参考"
- **策略二**：直接告知用户"未找到相关信息，无法为你提供准确回答"

### 5.2 混合检索：向量检索+关键词检索，互补长短

混合检索将向量检索和关键词检索（如BM25）结合起来，能互补长短。通过Reciprocal Rank Fusion（RRF）算法，将两种检索方式的结果进行融合排序。

向量检索擅长语义匹配，关键词检索擅长精确匹配。两者结合，几乎总是比单一检索方式效果好。

## 七、总结

RAG系统的效果优化，从来不是单一环节的优化，而是一个系统性的工程。query改写和基于检索结果的prompt构建，作为检索前和生成前的两个核心优化环节，虽然容易被低估，但却是提升RAG端到端效果最直接、成本最低的手段。
