# 一文吃透Prefill、Decode与KV Cache，大模型推理延迟优化必看

> 来源：https://m.toutiao.com/is/NUn6GkvYkW8/

## 大模型推理的两大核心环节：Prefill与Decode

### Prefill阶段：决定你多久能看到第一个回复
- 核心任务：接收全部提示词，处理并生成第一个输出字符
- 性能限制：**显卡算力**
- 核心指标：TTFT（首字符生成耗时）
- 算力不足→发送提问后迟迟看不到第一个回复

### Decode阶段：决定后续回复的流畅度
- 核心任务：逐个生成后续字符单元，直到回复完成
- 性能限制：**显存带宽和KV缓存**
- 核心指标：ITL（字符间隔耗时）
- 带宽不足→第一个字很快，后面的字慢慢悠悠

| 阶段 | 受限因素 | 核心指标 | 决定什么 |
|------|---------|---------|---------|
| Prefill | 算力 | TTFT | 第一个回复多久出现 |
| Decode | 内存带宽+KV Cache | ITL | 后续回复是否流畅 |

## 铺垫：大模型如何"读懂"输入

### 1. 字符拆分（BPE）
把文字切成字符单元并分配数字编号。高频词一个单元表示，生僻词拆成多段。字符单元数量直接影响Prefill运算量。

### 2. 向量转换
数字编号→特征向量（语义含义）。采用旋转位置编码（RoPE）标注位置顺序。

### 3. 注意力机制
- Q（查询向量）：当前文字需要调取什么信息
- K（键值向量）：当前文字能提供什么信息
- V（数值向量）：当前文字的实际输出内容

每段文字用Q匹配全文K，按匹配程度融合V，形成语义表达。

## KV Cache：推理速度的关键

### 核心作用：缓存复用，避免重复运算
- 无KV Cache：生成第N个字符需重新运算N次注意力 → O(N²)
- 有KV Cache：只需N次增量运算 → O(N)
- 生成1000字：有缓存1000次运算 vs 无缓存500500次

### 代价：占用显存
- 13B模型：单字符KV Cache ≈ 1MB
- 4096长度上下文：约4GB显存
- 10000字回复：约10GB显存

### 主流优化方式
1. **数据压缩**：FP16→INT8/INT4，减少75%显存占用
2. **滑动窗口**：超出范围的历史KV Cache丢弃
3. **GQA分组查询注意力**：多组共用KV，减少生成量
4. **分页注意力（PagedAttention）**：vLLM核心，按需加载释放

## 模型量化与推理框架

### 模型量化
- FP32→FP16/BF16：显存减半，Prefill+Decode都提升
- INT4量化：7B模型从28GB→4GB，笔记本也能跑
- 代价：精度损失，GPTQ/AWQ等方法尽量降低损耗

### 推理框架（vLLM/TensorRT-LLM/TGI）
1. **Continuous Batching**：用户A在Decode时同时处理用户B的Prefill
2. **Speculative Decoding**：小模型先生成，大模型核验修正
3. **KV Cache管理**：分页存储，避免碎片化

## 实战排查指南

### 第一步：判断卡顿类型
- **启动响应慢**（首字符迟迟不出）→ Prefill阶段 → 算力/输入过长
- **后续输出拖沓**（首字快后面慢）→ Decode阶段 → 带宽/KV Cache

### 第二步：针对性优化

**Prefill卡顿：**
1. 精简输入文本（压缩RAG上下文、精简系统提示词）
2. 提升算力（更强GPU/多卡并行）
3. 优化字符拆分词库
4. 模型量化（FP16/BF16）

**Decode卡顿：**
1. 优化KV Cache调度（分页/滑动窗口）
2. 提升内存带宽
3. 深度量化（INT8/INT4）
4. 接入高效推理框架

### 常见误区
- ❌ 盲目提升算力（Decode阶段算力不是瓶颈）
- ❌ 一味扩充上下文（增加Prefill运算量+KV Cache占用）
- ❌ 忽视字符拆分影响
- ❌ 量化精度越低越好（需平衡效果和效率）

## 总结
1. Prefill算力受限→TTFT，Decode带宽受限→ITL
2. KV Cache缓存复用是提速关键，但需优化显存占用
3. 量化用精度换效率，推理框架优化调度
4. 排查卡顿先判断阶段，再针对性优化
