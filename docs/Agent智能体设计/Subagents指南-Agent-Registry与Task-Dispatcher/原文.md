# 一、入门必懂：Subagents到底是什么

在正式深入技术细节之前，我们先搞清楚一个最基础的问题：Subagents到底是什么。

Subagents是一种中心化的多智能体协作架构，一个被称为"主管（Supervisor）"的主代理，将多个子代理包装成工具（Tools），通过工具调用机制调度子代理。主代理的核心职责是判断什么时候调用哪个子代理、传递什么参数，以及如何将各个子代理的返回结果组合起来，形成最终的用户响应。

要真正理解Subagents，就必须掌握它的四个核心特性：

## 1.1 集中控制：主代理是唯一的"总指挥"

Subagents架构中，所有任务的路由都必须经过主代理，不允许子代理"越级上报"。这就像公司里的所有工作汇报都必须经过项目经理，再由项目经理统一向客户或上级反馈。

## 1.2 无直接用户交互：子代理只负责"干活"

在Subagents模式中，子代理的核心作用是执行具体任务，它们不会直接与用户进行交互，所有的输入都来自主代理，所有的输出也都返回给主代理。

## 1.3 子代理即工具：复用现有基础设施

Subagents最灵活的一点在于，子代理是通过标准的Tool Calling（工具调用）机制被主代理调用的。这意味着，只要是LangChain支持的工具基础设施，都可以直接复用。

## 1.4 并行执行：大幅提升任务效率

与单智能体只能串行执行任务不同，主代理可以在单轮对话中同时调用多个子代理，让它们并行执行各自的任务。

## 1.5 关键区分：Supervisor和Router的区别

Supervisor（主管代理）是一个完整的Agent，会维护整个对话的上下文，在多个轮次的对话中动态决定调用哪些子代理。

Router（路由器）则相对简单，通常只是一个单一的分类步骤，根据用户输入的类型，把任务分发给对应的处理单元，不会维护持续的对话状态。

# 二、场景判断：什么时候该用Subagents

Subagents并不是银弹，它有自己的适用场景。结合实际开发经验，以下四种场景，才是Subagents模式的最佳应用场景：

## 2.1 多领域系统：需要处理不同类型的任务

如果你的AI系统需要同时处理多个不同领域的任务，比如同时处理日历管理、邮件发送、CRM客户管理、数据库查询等。

## 2.2 无需直接对话：子代理只需"干活"不沟通

如果场景中子代理不需要直接与用户交互，只需要负责执行具体任务并向主代理汇报结果。

## 2.3 集中式工作流控制：需要一个"总指挥"

如果任务是多步骤、有先后顺序的，需要一个"总指挥"来编排整个工作流程。

## 2.4 跨团队协作开发：不同团队各自维护Agent

在大型企业或复杂项目中，通常会有不同的团队负责不同的AI能力开发。

# 三、工具暴露模式：两种思路的对比与选择

在Subagents架构中，子代理最终是通过工具的方式暴露给主代理的，有两种不同的思路：

## 3.1 模式一：Tool per Agent（一个代理一个工具）

每个子代理都被包装成一个独立的工具函数，主代理通过调用不同的工具函数来调度对应的子代理。这种模式的优势是，能对每个子代理的输入输出进行精细控制。

## 3.2 模式二：Single Dispatch Tool（统一调度工具）

这是LangChain官方更推荐的一种模式，尤其适合代理数量多、跨团队协作的场景。它的核心思想是，通过一个统一的参数化工具来调用所有注册的子代理。

Single Dispatch Tool模式有三个明显优势：
- 支持跨团队独立开发
- 扩展性极强
- 强大的上下文隔离

# 四、核心模式：手把手搭建 Agent Registry + Task Dispatcher 系统

## 4.1 系统架构详解

整个系统的流程非常清晰，从用户输入到最终输出，共分为四个层级：
1. 用户输入
2. 主代理（Supervisor）：作为整个系统的"总指挥"
3. Task Dispatcher（任务调度器）：作为统一的调度入口
4. Agent Registry（子代理注册表）：存储所有已注册的子代理

## 4.2 完整代码实现

```python
from langchain.tools import tool
from langchain.agents import create_agent

# 第一步：不同团队各自创建子代理
research_agent = create_agent(
    model="gpt-5.4",
    prompt="You are a research specialist...",
    tools=[]
)

writer_agent = create_agent(
    model="gpt-5.4",
    prompt="You are a writing specialist...",
    tools=[]
)

reviewer_agent = create_agent(
    model="gpt-5.4",
    prompt="You are a code and document reviewer...",
    tools=[]
)

# 第二步：构建 Agent Registry
SUBAGENTS = {
    "research": research_agent,
    "writer": writer_agent,
    "reviewer": reviewer_agent
}

# 第三步：创建统一的 Task Dispatcher
@tool
def task(agent_name: str, description: str) -> str:
    """Launch an ephemeral subagent for a task."""
    agent = SUBAGENTS[agent_name]
    result = agent.invoke({"messages": [{"role": "user", "content": description}]})
    return result["messages"][-1].content

# 第四步：创建主协调代理（Supervisor）
main_agent = create_agent(
    model="gpt-5.4",
    tools=[task],
    system_prompt="You coordinate specialized sub-agents to complete user tasks..."
)
```

# 五、Agent规格管理：三种方式适配不同规模

## 5.1 System Prompt 枚举（最简单）

直接把所有可用的子代理列表写在主代理的system prompt中。

## 5.2 Dynamic Discovery（动态发现）

子代理注册到Agent Registry后，主代理可以通过统一的"list_agents"工具查询可用的子代理。

## 5.3 Tool-based Discovery（基于工具的发现）

通过一个统一的工具来调用所有子代理，主代理只需调用这个工具，传入agent_name参数来选择具体的子代理。

# 六、上下文工程：让子代理"读得懂"、"用得上"

## 6.1 子代理规格（Tool Schema）：主代理调度决策的关键

子代理的规格定义决定了主代理能否做出正确的调度决策。规格应包含：
- 名称（agent_name）：简洁且有描述性
- 描述（description）：明确子代理的职责、能力范围、适用场景
- 输入参数（input schema）：明确子代理需要的输入参数

## 6.2 子代理输入：传递足够的上下文信息

主代理传递给子代理的输入信息应包含：
- 任务描述：清晰描述需要子代理完成的具体任务
- 上下文信息：与任务相关的背景信息、前置结果等
- 输出格式要求：明确期望的输出格式

## 6.3 子代理输出：让主代理"用得上"结果

子代理输出是指子代理返回给主代理的结果，直接决定了主代理能不能"做好决策"。

# 七、执行模式：同步与异步的选择

## 7.1 两种执行模式对比

| 执行模式 | 主代理行为 | 适用场景 | 代价 |
|---------|-----------|---------|-----|
| 同步（默认） | 等待子代理完成任务后，再继续执行 | 主代理需要子代理结果才能继续 | 实现简单，但会阻塞对话 |
| 异步 | 发起子代理后台任务后，立即继续执行 | 子代理任务独立、用户不应等待 | 用户响应快，体验好，但实现更复杂 |

## 7.2 如何选择合适的执行模式

选择同步执行的情况：
1. 任务有顺序依赖
2. 主代理需要子代理的结果才能拟定回复
3. 子代理失败应阻止主代理回复

选择异步执行的情况：
1. 子代理任务是独立的
2. 用户不应等待
3. 需要并行运行多个独立任务

# 八、深入理解：上下文隔离的核心价值

Subagents模式的上下文隔离，主要体现在两个方面：

## 8.1 子代理无状态：所有记忆由主代理维护

在Subagents模式中，子代理是无状态的，它们不记得过去的交互，所有的对话记忆都由主代理维护。

## 8.2 独立上下文窗口：避免主代理上下文膨胀

在Single Dispatch Tool模式下，每个子代理调用都在一个独立的、干净的上下文窗口中运行。子代理完成任务后，只返回一个简洁的摘要给主代理。

## 8.3 子代理的状态延续（可选）

默认情况下，子代理使用继承的检查点模式，每次调用都从全新状态开始。但可以通过传递checkpointer=True参数，开启延续模式。

# 九、常见问题与解决方案（避坑指南）

## 9.1 问题1：主代理频繁调度错误的子代理

解决方案：
- 优化子代理规格
- 强化主代理引导
- 增加调度校验

## 9.2 问题2：子代理无法正确执行任务

解决方案：
- 完善子代理输入
- 优化子代理prompt
- 增加输入校验

## 9.3 问题3：主代理上下文窗口膨胀

解决方案：
- 规范子代理输出
- 启用上下文隔离
- 主代理上下文清理

## 9.4 问题4：子代理之间无法协同

解决方案：
- 明确子代理职责划分
- 优化主代理任务拆解
- 增加任务调度日志

## 9.5 问题5：异步执行模式下任务状态管理混乱

解决方案：
- 定义统一的任务状态
- 搭建任务状态管理模块
- 添加任务失败重试机制

## 9.6 问题6：跨团队开发时子代理注册和维护混乱

解决方案：
- 制定子代理注册规范
- 搭建统一的Agent Registry管理平台
- 增加版本控制

# 十一、总结：Subagents的核心价值与未来展望

Subagents模式的核心价值在于"分工协作"和"上下文隔离"：
- 通过主代理与子代理的分工，让每个智能体专注于自己的核心任务
- 通过上下文隔离，避免主代理上下文膨胀

从未来发展来看，Subagents模式将成为多智能体协作的主流架构之一。
