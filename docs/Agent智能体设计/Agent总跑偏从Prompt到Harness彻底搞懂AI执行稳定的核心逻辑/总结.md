# Agent总跑偏？从Prompt到Harness，彻底搞懂AI执行稳定的核心逻辑

## 核心要点

### 1. 三层工程化防护圈：不是替代，而是嵌套

Agent跑偏从来不是单一因素导致，**Prompt → Context → Harness** 三层逐层外扩，共同支撑Agent稳定运行：

| 层次 | 解决什么问题 | 类比 |
|------|------------|------|
| Prompt Engineering | 指令表达，让模型理解你的意思 | 怎么把工作要求说清楚 |
| Context Engineering | 输入环境，让模型拿到正确信息 | 合适时间给合适的信息 |
| Harness Engineering | 运行系统，让模型稳定做对 | 搭建系统保障长期稳定 |

### 2. Prompt Engineering：五大手段解决"说清楚"

- **角色设定**：给模型明确身份，划定行为边界
- **输出格式约束**：避免格式混乱，按需输出表格/清单/段落
- **示例驱动**：少样本学习，降低理解难度
- **任务拆解**：大任务拆小步骤，避免顾此失彼
- **明确成功标准**：让模型知道"做到什么程度才算合格"

**局限性**：只解决表达问题，无法应对信息缺失和长链路执行稳定性问题

### 3. Context Engineering：四大实践管好"信息弹药"

核心原则：**上下文是有限资源，越准越好，非越多越好**

- **RAG**：先检索再生成，解决知识滞后问题
- **历史上下文压缩**：保留关键信息，删除冗余
- **运行时按需检索**：不提前塞满，按需供给
- **Progressive Disclosure**：渐进式披露规则，避免信息轰炸

**关键概念**：context rot（上下文腐化）—— 上下文窗口越长，模型注意力越稀缺，容易丢重点

### 4. Harness Engineering：六层结构保障"稳定执行"

```
┌─────────────────────────────────────────────────┐
│ 第6层：约束、校验与失败恢复 — 容错机制          │
├─────────────────────────────────────────────────┤
│ 第5层：评估、观测与验收 — 自我认知闭环          │
├─────────────────────────────────────────────────┤
│ 第4层：状态、记忆与交接 — 清晰的任务记忆        │
├─────────────────────────────────────────────────┤
│ 第3层：执行编排 — 6步闭环执行流程               │
├─────────────────────────────────────────────────┤
│ 第2层：工具系统与动作空间 — 清晰好用的工具      │
├─────────────────────────────────────────────────┤
│ 第1层：目标与信息边界 — 清晰的方向              │
└─────────────────────────────────────────────────┘
```

### 5. OpenAI实践：把"环境可读性"做成系统能力

- 仓库知识变成**目录索引**，而非百科全书
- 让Agent能看见UI、日志、指标，建立反馈闭环
- 架构约束+lint，把经验变成系统规则
- AI slop自动化垃圾回收，避免系统漂移

### 6. Anthropic实践：生产和验收必须分离

- **context anxiety**：上下文接近上限时，模型会草率收尾
- **context reset**：必要时换新Agent，通过交接文档继续
- **self-evaluation bias**：自评不可靠，生成和验收必须分离

### 7. 排障思路：从"调模型"到"搭系统"

当Agent跑偏时，按序排查：
1. 目标是否清楚？成功标准是否可验证？
2. 模型是否拿到当前步骤真正需要的信息？
3. 工具接口是否清晰？返回是否可读？
4. 执行流程是否明确？有关键节点校验？
5. 是否有评估验收机制？
6. 是否有容错机制？

---

## 关键结论

**三者不是替代关系，而是互补的嵌套关系**：
- 任务越简单，Prompt作用越明显
- 任务需外部信息，Context作用越关键
- 任务越长链路、越复杂，Harness作用越不可替代
