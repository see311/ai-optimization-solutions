# 这个 Skill 刚开源就爆火，Agent 联网能力直接拉满！

最近半年，我每天大部分时间都在跟 Claude Code、Codex 这类 AI Agent 打交道。

写代码场景下，它们表现确实惊艳。

但只要任务一沾到「联网」，体验立刻打回原形。

举几个亲身踩过的坑。

让它去某个产品官网拉资料，结果打开是登录墙，直接返回一句「无法访问」。

让它去某社交平台查竞品账号的最新动态，搜出来全是过期缓存，登录后才能看的内容根本够不着。

更别提让它帮我在创作者平台发图文了，最后还是得自己手动复制粘贴。

问题其实很简单。

市面上大部分浏览器 Agent，跑的都是新起的无痕浏览器，登录态、Cookie、扩展，什么都没带。

等于给了 AI 一双眼睛，却没给它能进门的手。

直到前几天，我在 GitHub 上发现了 **Web Access** 这个项目。

它的定位很巧妙，不是又造一个浏览器 Agent 框架，而是做成一个 Skill。

兼容 Claude Code、Cursor、Gemini CLI、Codex CLI 等所有支持 Skill 协议的 Agent。

而它最反常识的设计在这里。

它通过 CDP（Chrome DevTools Protocol）协议，**直接接管我们日常在用的那个 Chrome** 。

不起新进程，不开无痕窗口，就用我们桌面上那一个浏览器。

这意味着 AI 拿到的，是我们已经登录的小某书、已经登录的飞书、已经登录的公司内部系统。

Cookie、扩展、书签、历史记录，全都现成可用。

相当于给 AI 装上了我们的「眼睛和手」，而不是塞给它一个空壳浏览器。

具体能力分三层，每层都对应一个我实际在用的场景。

**第一层是工具自动调度。**

Skill 里写了一套策略提示，让 LLM 自己根据任务判断走哪条通道。

简单搜索走 WebSearch，纯文本页面走 Jina 节省 token，要登录、要交互的，才走 CDP。

对应场景：让它同时调研 5 个产品官网做对比，子 Agent 并发执行，共享一个浏览器代理，tab 级隔离。

**第二层是真实浏览器操作。**

提供三种点击方式：JS click、CDP 真实鼠标事件、文件上传。

为什么要区分？因为 JS click 容易被社交平台风控识别成机器人。

CDP 真实鼠标事件走的是系统级输入，跟人手点击几乎一模一样。

对应场景：让它在某书创作者后台发一篇图文，从上传图片到点击发布，全流程托管，不用我手动接管。

**第三层是站点经验积累。**

AI 每操作完一个站点，会自动按域名记下经验：URL 模式、平台陷阱、已知坑点。

跨 session 复用，越用越懂。

对应场景：第一次让它发某书踩了几个坑，第二次再用就丝滑很多，不用再从头摸索。

最近 2.5.0 版本还加了个让我眼前一亮的功能。

那就是**本地 Chrome 书签和历史检索** 。

这个场景太真实了。

我们经常会跟 AI 说「帮我打开公司那个 XX 平台」，但公网上根本搜不到。

有了这个能力，AI 可以从本地 Chrome 的书签和历史里按关键词查 URL，精准定位。

安装过程设计得相当克制。

推荐方式是用 skills 这个开源 CLI 工具，一行命令搞定：

```
npx skills add eze-is/web-access
```

它会自动识别 Agent 环境，装到正确的位置。

懒得动手的，直接把这行命令甩给 Agent，让它帮我们装也行。

CDP 模式需要 Node.js 22+，并在 Chrome 地址栏打开 chrome://inspect/#remote-debugging，勾选允许远程调试。

整个前置配置加起来不超过 2 分钟。

不过有一点必须客观提醒。

作者在 README 里也写得很明白，用浏览器自动化操作社交平台（例如小某书）存在被限流甚至封号的风险。

强烈建议先用小号试水，别拿主力账号开盲盒。

# 写在最后

聊聊我对这类项目的看法。

Web Access 真正有意思的地方，不只是好用，而是它打开了一个新的设计范式。

「让 AI 借用我们的环境去干活」，这个思路其实可以迁移到很多地方。

未来会不会有 Skill 接管我们的 IDE？接管我们的设计软件？接管我们的命令行环境？

但这条路也藏着一个新的问题。

把日常 Chrome 的钥匙交给 AI，到底是效率红利，还是一道新的安全边界？

这个答案，可能要靠每个使用者自己去掂量。
